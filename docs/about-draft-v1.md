## 長版

### 一、起點

【待補:第一次寫程式是什麼時候、為了什麼?是課堂作業、打工需求,還是自己想做某個東西?
這一段的作用是讓讀者知道你不是被規劃出來的,而是從某個具體的動機開始的——
越具體越好,例如「大一想幫某個社團做報名表,用 Google 表單做不到某件事」這種等級。】

【待補:為什麼是後端 / 系統這一側,而不是視覺或演算法?什麼時候發現自己喜歡的是這個?】

### 二、系友會平台——第一次有人把正在用的東西交給我

2024 年 8 月接手系上的系友會平台。【待補:怎麼接到的?老師找、學長交接,還是自己提的?
當時那個系統是什麼狀態、有沒有人在用?】

接手後第一件讓我背脊發涼的事,是那套權限設計:DRF 的全域預設是 `AllowAny`,
然後一個端點一個端點去加鎖。這在紙上看起來只是順序問題,實際上是整片攻擊面預設打開——
只要有人新增端點時忘了加那一行,就破了,而且不會有任何錯誤訊息告訴你。

上線前那輪資安審查列了 SEC-001 到 SEC-030,我一條一條修完,
最後把全域預設翻成 default-deny:先全部拒絕,要開放的明確寫出來。
這個順序後來變成我每個專案的第一天就做的事。

同一個專案也給了我一個不太光彩的教訓。前台是 CRA 配上我自己刻的預渲染管線,
能跑,但很脆:路由要手動維護一份、還綁死在某個 Chrome 版本上,每加一頁都要記得去改另一個地方。
它撐到上線,但我知道那是靠紀律撐的,不是靠設計。重來我會直接選有原生 SSG 的框架,
把那整條管線刪掉——你現在在看的這個站就是這樣做的。

### 三、設備借用系統——資料搬進來的那天

【待補:這個系統原本是怎麼運作的?紙本、Excel,還是舊系統?是誰在用、一天大概幾筆?】

最有記憶點的是資料遷移。舊資料搬進新結構時跑出 9,138 筆成功、2,271 筆失敗,
我一開始以為要逐筆看,結果攤開錯誤報表才發現幾乎全是同一種問題:某個欄位是空的。
真正的修法不在匯入端,在 mapper——先清洗再匯入,那份兩千多筆的錯誤報表根本不會存在。
我現在看到長長的錯誤清單,第一個反應是先數種類,不是先數筆數。

另一件事比較難承認。這個系統的後期 UIUX 稽核點出了重複的頁面,
還有幾個地方在畫面上顯示假資料——那是我前期為了趕功能堆出來的債。
把錯誤靜默成「一切正常」,比直接壞掉危險得多,因為沒有人會來報修。
這些現在有編號、有清單,正在還。我把它寫在這裡,是因為沒還完。

### 四、日秀美學——第一次有人為我寫的東西付錢

2025 年 6 月進日秀美學,做 AI 美甲平台跟一套多租戶的人資系統。
【待補:面試 / 進去的經過?當時你有什麼是他們要的?第一週被交付的第一件事是什麼?】

人資系統那套是我目前寫過最大的東西:36 個功能模組、241 個資料模型,
驗收時實測了 728 個端點,通過率 87.5%——沒過的那部分我也記在案例頁上,沒有四捨五入掉。

其中一個發現我到現在還常想起來。薪資 API 有做快取,但快取鍵裡沒有使用者身分。
意思是:在同一個 TTL 窗內,一個普通員工發出的請求,可能直接命中管理員剛剛留下的快取,
拿到全公司的薪資。它不會報錯,不會變慢,測試也全綠——它只是在某些時刻把資料送給不該看的人。

修法很短,在快取裝飾器加一個 `vary_by_user` 把身分折進鍵裡,然後寫一個用真實 HTTP 呼叫的回歸測試,
證明兩個使用者永遠看不到對方的快取。但我從這件事學到的比那行程式多:
**快取設計就是權限設計**。在多租戶系統裡,這類錯誤不是效能問題,是資料外洩。

再往回追,根因其實在資料模型:全域角色跟租戶角色兩套並存,才連帶長出提權跟跨租戶的問題。
重來一次,我會從第一天就把權限統一設計在租戶這個維度上。

### 五、Naily——接手別人寫的程式碼

Naily 前面 198 個 commit 不是我的。2025 年 11 月起我接手獨立維護,到現在 121 個。
接手跟從零開始是兩種完全不同的工作:從零開始你只要說服自己,接手你得先搞懂別人為什麼那樣寫,
而且有一半的原因是不會寫在程式碼裡的。

我做的第一件事不是重構,是把慣例寫下來。規則明文化之後,每一次修改才會讓系統更一致,
而不是各自往不同方向發散——重構是在那之後才安全。

接手後我做的是 App 前端:把幾個數千行的巨檔拆開(訂單詳情 5,256 行拆到 230 行、
購物車/結帳/訂閱結帳三支合計 6,800 行拆到 1,200 行加獨立元件)、補上 401 攔截刷新讓 token
過期不再把人踢出去、上架前的安全硬化與 CI/CD。裝置端的 AI 指甲辨識與 AR 試戴是另一個團隊的工作,
不是我的——這件事我在案例頁上寫清楚了,因為把別人的成果掛在自己名下,
比少寫一項專長傷害大得多。

【待補:這一節現在少了一個「難題」。有沒有哪一次前端的決定是你想很久的?
例如那個 800 行上限是怎麼訂出來的、拆訂單詳情時最難切的是哪一塊、
或是接手初期哪一個地方讓你看了三天才懂原團隊為什麼那樣寫?】

還有一件小事讓我改了習慣:這個專案的 CHANGELOG 是事後補寫的,日期跟實際 commit 對不上。
值得留的記錄應該跟著 tag 一起產生,不是回頭湊。我現在相信 git,不相信散文。
